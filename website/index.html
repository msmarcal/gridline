Ubuntu LTS · Wayland · apt only

A tiling session that is just a package away.

Gridline is an optional Wayland tiling desktop for Ubuntu LTS, inspired by Omarchy and Regolith, delivered exclusively as Debian packages. Install it, pick it at the login screen, and your stock GNOME session stays installed, selectable, and supported as the fallback. 

$ sudo apt install gridline-desktop

That one-liner is the target, not the present: the packages are not in a PPA yet, and this site does not pretend otherwise. Today the honest path is building the source package, which takes minutes on Ubuntu 26.04.

waybar on top. hyprland tiles below. all of it from the Ubuntu archive.

Why it exists

You already use Ubuntu and you like using it. You work in the terminal. You saw Omarchy and wanted that. Today your choices are to leave Ubuntu for a rolling base, or to assemble the stack by hand and maintain it yourself forever. Gridline is the third option: the Omarchy-like experience as apt packages on the Ubuntu you already run, with the Ubuntu session sitting intact beside it in case you want out.

It is a personal project with a small audience by design, the way Omarchy's is. That is the nature of the thing rather than a problem to solve.

Design rules

These are constraints the project holds itself to, not aspirations. They exist because you are going to run this on the machine you work on, and an experimental desktop should not be able to leave you without a computer on a Tuesday morning.

debs only

No install script, no post-install download, no manual file copying. If it cannot ship in a package, it does not ship.

GNOME stays

Installed, selectable, and supported. Gridline is additive and removable, and no change may replace or remove the Ubuntu session.

no edits to others' files

GDM, PAM, NetworkManager, PipeWire, and polkit are influenced only through named drop-ins under paths Gridline owns.

archive packages first

Preferred over third-party sources, so what is installed is what Ubuntu ships.

one compositor, one boundary

Hyprland sits behind an adapter in a single location, and a build gate fails the build if a compositor name escapes it.

How it works

Everything Gridline ships is a Debian package. When you pick Gridline at the login screen, a small launcher starts the compositor and then checks, against the running session, that every piece the desktop promises is actually there: locking, idle detection, output management, screen sharing.

If a piece is missing, the session says so. The launcher writes which piece failed to the system journal and returns you to the login screen, where your usual Ubuntu session is still one click away. Gridline would rather not start than start as a broken desktop you cannot explain.

Rice it

The shipped defaults live under /etc/xdg/gridline/, and anything you write in ~/.config wins over them. That is verified behavior, not a promise: the session was measured preferring a user's own configuration over what the packages ship.

The shell is stock archive software: the bar is waybar, the notifications are mako, the wallpaper is hyprpaper, the launcher is fuzzel. Every upstream document and every dotfile the community has written for them applies to Gridline unchanged. Configuration resolution, including where the compositor's own file is searched, is written down in configuration.md.

The terminal is a recommendation rather than a dependency, and that is a practical difference: removing the one Gridline prefers leaves the session installed and working. The keybinding names no terminal at all. It asks the freedesktop mechanism for the terminal this machine uses, so you change yours by registering one, not by editing anything of Gridline's.

The support gap, stated plainly

Every piece of the compositor stack Gridline depends on (Hyprland, its portal backend, the Wayland tools) comes from Ubuntu's universe component. Canonical does not commit to security updates for universe; it does for main. So a Gridline install inherits no CVE-response commitment for its compositor, locker, or portal backend.

Patching those is your responsibility, the way it already is for anything tiling you would install by hand today. A Gridline-maintained PPA tracking upstream CVEs is recorded as a future goal, not a promise. This gap is a design fact of the project, recorded in its documentation, and this site does not hide it.

Status

Early development, in the open. Verified end to end in a virtual machine with no 3D acceleration, including the failure path, and not yet on hardware. Everything below was measured on that one machine, which is worth knowing before reading the checkmarks:

  • GDM session entry, launcher, and capability gate
  • Hyprland adapter behind the compositor boundary
  • Status bar: workspaces, clock, and network, read off the screen and matched against the system's own view
  • Styled notifications; critical ones stay until dismissed
  • Wallpaper anchored to the release's own image. On the test machine the wallpaper daemon crashes, because a graphics buffer allocation is refused without 3D acceleration; it has not been checked on hardware
  • Application launcher on SUPER D, command menu on SUPER SHIFT D; the menu dispatches on entries, not typed text, so a free-typed word that matches nothing cannot fire a destructive action
  • Fail-safe screen lock: a locker that exits without an unlock is replaced, so a crashed locker never leaves the session unlocked
  • Session hygiene: shell components start only in a Gridline session, and the stock Ubuntu session was measured untouched
  • A diagnostic that says when it last looked: gridline doctor reports each component with the time its state was recorded, so “running” is a statement about now rather than about when you logged in
  • Removal puts the machine back: the components Gridline turns off are turned on again, and removing it was measured leaving the GNOME desktop untouched
  • Every push checked without a person: the packages build, six gates run, installing and removing is measured against the machine, and the session's wiring is verified — on a clean runner, in about a minute
  • The keys printed on the laptop: volume, mute, microphone, brightness and media are bound. Volume was checked with a person on the key: one press is one step, holding repeats and stops at 100 percent, and a volume key unmutes, because a key that moves a number nobody can hear has not done its job. Mute reached the compositor once in four attempts. Brightness, the microphone and the media keys are unexercised: the test machine has no backlight and its speakers and microphone are the same dummy device. No on-screen indicator yet
  • Portal integration
  • Full configuration defaults

Everything is planned as tracked changes, not vapor.

A green run means the packaging and the wiring are intact. It does not mean the desktop works: the automated run has no screen, so the compositor starting, the bar drawing and the lock screen are all unchecked, and someone still has to log in. What it cannot see is written down rather than left for you to discover.

Whether the graphical half could be checked automatically was asked of a hosted runner rather than argued about. The expensive part turned out to be free: the runner already has a display device and will load a virtual one on request. The compositor still aborts on it, in its backend, with no Wayland socket to show for it. So that half stays unchecked, for a measured reason, and the question can be asked again with one click when the compositor, the kernel or the runner changes.

Known issues

Stated here because a project that lists only what works is describing a different project.

The compositor crashes when a session ends. On the test machine it happened 25 times across 27 sessions, always the same signature in the compositor's graphics backend library, always within a minute of the session closing. It predates the desktop shell. The test machine has no 3D acceleration, so whether it happens on hardware is not known, and finding out is the first thing the open change on it does. The cost to you is probably a crash report on the next login. Nothing has been observed to be lost, and nothing has been looked for yet.

The change is in the repository, with the measurement that opened it.

Everything on this page was measured on one virtual machine. There is no result from a laptop yet, and a laptop is where a person who just installed Ubuntu will be.

Follow along

The source repository holds the code, the OpenSpec change history, and the design documents. The design is written down before it is built, so the repository reads as a record of decisions, not just commits. The canonical development home is a self-hosted Forgejo mirror that receives the same history; GitHub is where the project is visible, and where the checks run — the self-hosted side has no runner, so a push there is unverified until it arrives here.

The record includes the dead ends. Where a measurement contradicted what the project had written down, the correction is kept beside the claim rather than replacing it, because the reason something changed is usually worth more than the change. The first clean automated run found a build dependency the author's own machine had been quietly supplying for weeks, which is the kind of thing a project only learns from a machine that has never seen it before.
