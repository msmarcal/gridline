# Tasks

## 1. The measurements the design left open

- [x] 1.1 The search order is carried by `libhyprutils.so.10`, which references `XDG_CONFIG_HOME`, `/.config`, `XDG_CONFIG_DIRS` and `/etc/xdg`, measured with a fabricated variable name as a negative control. The per-program subpath is `hypr/hyprland.conf`, taken from compositor logs of earlier sessions which name the file in use: `/home/ubuntu/.config/hypr/hyprland.conf` on one login and `/etc/xdg/hypr/hyprland.conf` on another.

  **The check is the whole order, not only the user's paths.** Naming our path when an administrator has placed a system-wide compositor configuration would override them, and freeing that path for an administrator is one of the reasons this change exists. So the rule is: name Gridline's path only when the compositor would otherwise find nothing.

  When a path cannot be evaluated, for instance with `HOME` unset, it counts as absent, which is what the compositor's own search would conclude from the same state
- [x] 1.2 **They do not differ, and the answer is worse than either guess: dpkg leaves the file.** Exercised by building a version of the package that drops the manifest line and upgrading onto it.

  Unmodified: the file is still at `/etc/xdg/hypr/hyprland.conf`, the directory is still there, and `dpkg-query` still lists it as a conffile of the package. Edited: identical, with the edit intact and no `.dpkg-*` written. An obsolete conffile is left alone in both cases.

  **So removing the manifest line fixes nothing on a machine that already has Gridline.** A fresh install would be clean and an upgrade would not, and the compositor would still find the file and still read Gridline's defaults into every session. Testing only a fresh install is how this would have shipped. The implementation needs `dpkg-maintscript-helper rm_conffile`, which is group 2's work and is the thing this task existed to find.

  Two further behaviours met while restoring the machine, both worth knowing for the same reason: `--reinstall` does not overwrite a conffile the administrator has modified, and does not recreate one the administrator has deleted. The second needs `--force-confmiss`. A restoration that reports success without comparing checksums will be wrong in both cases, as this one was until it compared
- [x] 1.3 Confirmed without starting a session, using `--verify-config`, which parses and reports rather than running. Pointed at a file containing an invalid line it answers `Config error in file /tmp/bad.conf at line 1`, **naming the file**, which is what distinguishes read from ignored; pointed at a valid one it answers `config ok`.

  That is a better instrument than the task asked for. Observing a running compositor would have meant starting one, and an earlier session in this project left an orphaned headless instance holding the screen doing exactly that

## 4. A gate for Gridline-named declared paths

- [x] 4.1 `tools/check-declared-paths`, wired into the build beside the other two. It reads every `.install` and `.dirs` manifest, computes the installed path, and fails when no segment carries the project name. Twelve paths checked today and none reprove.

  Verified by planting rather than by passing: a directory in another component's tree with no Gridline segment fails the check and the build, naming the manifest and the path
- [x] 4.2 Both shapes are in the tree and both pass. `/etc/xdg/gridline/compositor/defaults.conf` passes on the directory segment; `/usr/share/wayland-sessions/gridline.desktop` and `/usr/share/xdg-desktop-portal/gridline-portals.conf` pass on the filename while their directories belong to other packages, which is the drop-in shape the requirement blesses.

  A third case is worth recording because it looked like it might fail and does not: `/usr/libexec/gridline/adapters/hyprland/adapter` has neither a Gridline filename nor a Gridline leaf directory, and passes on an ancestor segment. That is the rule being "some segment" rather than "the name or the directory"
- [x] 4.3 Planted the same shape the change removes, a file into the compositor's own directory under `/etc/xdg`, and the check failed the build naming the manifest and the path. The claim that a gate would have caught this on the day it shipped is now demonstrated rather than asserted
- [x] 4.4 Recorded: the check tests a name, not whether the directory a Gridline-named file lands in is one the owning component actually reads. A Gridline-named file dropped into an unrelated directory passes and is still wrong, and no pattern decides that.

  The header also records something the writing of it demonstrated. An earlier version named the offending path as its motivating example, and the isolation check failed the build on the comment. That is two gates composing rather than one getting in the way, and it is the third time in this project that explaining a compositor-specific decision outside the adapter has tripped that check

## 5. The terminal a Gridline session opens

Measured: 114 candidates, with the three installed terminals at positions 9, 76 and 102. Installing or removing an unrelated application could change which terminal a Gridline keybinding opens.

  That is a stronger finding than the task expected and it changes what the fix is for. The problem was never that the wrong terminal won; it was that the winner was arbitrary and unstable.

  One more thing the same output showed: `/usr/share/xdg-terminal-exec/` already held `gnome-`, `sway-` and `ubuntu-xdg-terminals.list`. Other desktops name their terminal and **Gridline was the only session falling through to the arbitrary list**, which means changing the declared package without naming a preference would have left the instability untouched

## 6. The administrator who edited the file

- [x] 6.1 With `rm_conffile` declared, an upgrade from the version that shipped the file reports `Removing obsolete conffile /etc/xdg/hypr/hyprland.conf` and the file is gone, leaving the directory empty. Without it, task 1.2 measured the file simply staying, so the helper is what makes the difference rather than the manifest change
- [x] 6.2 **The two cases differ, and only because the helper is there.** With the file edited, the upgrade reports `Obsolete conffile /etc/xdg/hypr/hyprland.conf has been modified by you` and keeps the edit as `hyprland.conf.dpkg-bak`, confirmed by finding the edit line in that file afterwards.

  That is the outcome worth having: the leak closes even for an administrator who customised the file, and nothing they wrote is destroyed. The backup is not read, because it no longer carries the filename the compositor searches for. What they have to do is nothing, unless they want their changes back, in which case the content is there to move
- [x] 6.3 Recorded in `docs/configuration.md`, under the section on shipped defaults being conffiles, which is where the rule it extends already lives. It states the dpkg behaviour that a reader would not guess, that an obsolete conffile is left in place without the helper, gives both upgrade outcomes in a table, and says plainly that nothing written is destroyed and nothing written is still in effect. It names the one file this happened to and points at `recovery.md` for what changed for a session outside Gridline

- [x] 7.1 Seven scenarios, counted from the delta file. All exercised, none deferred.

  *The keyboard works on first login*: a login with nothing of the compositor's own present loaded Gridline's defaults with forty bindings, and `SUPER + Return` opened the declared terminal. *Gridline's defaults are the ones in effect*: the log names `/etc/xdg/gridline/compositor/defaults.conf` and `gaps_in` reads 4. *A first login presents no upstream project messaging*: the suppressions ride in the same file and were read back from the running compositor. *A suppressed warning is recorded rather than erased*: unchanged by this change, the records are where the previous change put them. *A user's own configuration does not silently discard the defaults*: with a user file present the compositor loaded theirs and Gridline named nothing, and the marker was absent in both the terminal and the user manager, which is the detectable half. *The defaults reach no session but Gridline's*: the configuration a session outside Gridline produces is byte for byte the pre-Gridline file. *Absent defaults degrade rather than block*: unchanged in mechanism, and the reporting half remains owed to `add-session-health-check` exactly as the previous change recorded
- [x] 7.2 The name stayed and the meaning changed, deliberately, and the new meaning is what was measured. The old scenario described a component resolving by first file wins and asked that the defaults survive or their absence be recorded; the new one asks that the user's configuration be the one in effect and the absence be readable. Both halves exercised in the second branch of task 2.1.

  The validator is what forced this to be deliberate. A first draft replaced the scenario with two new ones, and `openspec validate` refused, because a MODIFIED block replaces the whole requirement and dropping a scenario has to be visible rather than incidental
- [x] 7.3 Rewritten. The section now describes naming the path rather than placing a file where the component searches, with the three consequences that follow, and says plainly that the precedence rule is Gridline's rather than the component's, since the compositor has no way to express "use mine unless theirs exists".

  One mention of the loader survives on purpose: a closing paragraph recording that the earlier arrangement existed, worked, and had two faults that appeared later. A reader who met the old mechanism should be able to tell it was replaced rather than find it deleted
