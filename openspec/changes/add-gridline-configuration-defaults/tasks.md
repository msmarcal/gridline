# Tasks

## 1. The measurements the design rests on

These come first because the rest is built on their answers. A task here that returns an unexpected answer changes the design rather than being worked around.

- [x] 1.1 **It does.** `source = /etc/xdg/gridline-test/sourced.conf` in a configuration file put `general:gaps_in` at the sourced file's value, read back with `hyprctl getoption general:gaps_in`. Exercised on three paths, because they are not the same path and an earlier reading treated two of them as one: `hyprctl keyword source <abs>` at runtime, `hyprctl reload` reparsing a file carrying the directive, and a real compositor startup from `/etc/xdg/hypr/hyprland.conf`. All three applied the sourced value.

  **The startup run also settled the ordering the design depends on.** The test file set `gaps_in = 23` and then sourced a file setting `17`; the session came up at `17`, so the later statement wins. A user who sources Gridline's defaults and writes overrides after them gets their overrides, which is the customization story the loader rests on, and it is now measured rather than assumed.
- [x] 1.2 **Nothing in `hyprctl` names the configuration file**, which is the first half of the answer and was checked before reaching for a workaround: there is no subcommand that reports the loaded path, `systeminfo` does not mention it, a `$VARIABLE` set by the configuration is not readable (`hyprctl getoption` answers `no such option`, the same answer it gives for an option that does not exist), and `set: true` is reported even for options no configuration touched, so it does not mean "the configuration set this".

  **What does work is `env =`.** A marker declared in Gridline's configuration appears in the environment of every process the compositor launches, confirmed as `GRIDLINE_CONFIG_PROBE=etc-xdg` in a client's `/proc/<pid>/environ` after a real startup. Anything running inside the session therefore has it as an ordinary environment variable and needs to read no files at all.

  Two readings along the way were wrong and are recorded because each would have closed this task with the wrong answer. The marker is absent from the **compositor's own** environ, which says nothing: `env =` is for the processes it launches, and `WAYLAND_DISPLAY` is missing from the same place for the same reason. And a same-user read of a child's environ under `su` returned `Permission denied`, whose `||` branch printed "marker absent" when the marker was in fact there.
- [x] 1.3 **Confirmed, with one fact the document does not carry.** With the user's file moved aside, a real session startup took its configuration from `/etc/xdg/hypr/hyprland.conf`, shown by the sourced value being in effect. With the user's file present, the compositor's own autogenerated configuration was what ran throughout every earlier verification in this project, which is the other half observed rather than staged.

  The new fact: when `/etc/xdg/hypr/hyprland.conf` exists, the compositor writes **no** autogenerated file into the user's directory. Only the moved-aside file remained there afterwards. So a first login on a machine with Gridline's defaults installed does not leave a competing user file behind that would win on the next login.

  Both test files were removed and the removal was verified rather than announced: an audit for files under `/etc/xdg` owned by no package reports none. That audit is the reason this did not go wrong. The first cleanup command reported nothing and left both files in place, most likely having killed its own shell with a `pkill -f` pattern, and the echo that was supposed to confirm the removal never ran.
- [x] 1.4 **The round trip works and needs no privilege.** `SetLockedHint b true` then `b false`, with `LockedHint` read back after each, went `false` -> `true` -> `false`, and `loginctl show-session -p LockedHint` agreed. Exercised as root first and then, which is the half that matters, from a process inside the session: the user sets it with no polkit prompt and no error, so the lock entry point needs nothing it does not already have.

  **The path is `/org/freedesktop/login1/session/self`**, which resolves from inside the session and is what the implementation uses. An earlier check reported it missing, because it was run from a shell that belongs to no session, where `self` has nothing to resolve to. Where an explicit path is needed instead, `Manager.GetSession` returns it for a session id and avoids having to know the escaping rule, which is not per character: session `22` is `_322`, a `_3` prefix on a leading digit rather than every digit escaped. `XDG_SESSION_ID` is present in the environment of a process the compositor launches, so the id is available without searching for it.
- [x] 1.5 **Confirmed, re-read from the archive rather than cited.** `dpkg-deb -f` on the downloaded packages: `swayidle` depends on `libc6`, `libsystemd0`, `libwayland-client0` and `libwayland-server0`, and on no Hyprland library; `hypridle` depends on `libhyprlang2` and `libhyprutils10`, which is the measurement the previous change recorded and the reason to choose differently.

  The manual documents `timeout`, `lock`, `unlock`, `before-sleep`, `after-resume` and `idlehint`, which covers every direction this change needs to route: inactivity, the logind `Lock` signal, and suspend. Two of those are conditional on the build having systemd support, and the dependency on `libsystemd0` is what says this build has it, so the conditional is satisfied rather than hoped for.

  It documents nothing that sets the **locked** state, which is why 1.4 exists: `idlehint` sets `IdleHint`, a different property answering a different question.

## 4. Locking happens without being asked

- [ ] 4.1 Declare the idle daemon as a dependency of `gridline-session` and verify with `dpkg-deb -f` on the built package rather than by reading the control file
- [ ] 4.2 Author the lock entry point, setting `LockedHint` true before the locker starts and false after it exits. Verify the false path runs whatever the exit reason, by exercising a normal unlock and a killed locker and reading the property after each
- [ ] 4.3 Route the idle timeout, the suspend hook and the key binding through that one entry point, with the binding asking logind to lock rather than running the locker. Verify by reading the journal for a lock triggered each of the three ways and confirming the same entry point ran
- [ ] 4.4 Verify the session locks itself after the configured period, timing it rather than assuming, and that authentication is required to return
- [ ] 4.5 Verify `LockedHint` reads true while locked and false after unlocking, which is the debt `add-session-lifecycle-integration` recorded and could not close
- [ ] 4.6 Verify the hint is not left true when the locker fails to start, since a system that believes an unlocked session is locked is the failure this ordering exists to prevent
